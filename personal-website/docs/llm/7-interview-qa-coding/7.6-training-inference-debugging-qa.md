# 7.6 分布式训练与推理故障排查实战题 (Debugging & Ops)

> [!IMPORTANT]
> **为什么要考察故障排查 (Troubleshooting)？**
> 架构设计可以背，代码可以刷，但**线上故障排查能力是检验候选人是否拥有大规模 GPU 集群“实操血泪史”的唯一标准**。在面试高级/专家级 AI Infra 工程师时，面试官往往会抛出一个真实的线上事故：“跑了半个月的千卡集群突然 Hang 住了，你怎么查？” 本章将带你沉淀一套教科书级的排查方法论。

## 🔥 2. 高频面试真题与满分回答

### ❓ 真题 1：千卡集群训练中，突然所有 GPU 利用率降为 0，程序 Hang 住，如何排查？
**[面试官意图]** 考察候选人对 NCCL 通信机制、环境变量、监控系统的熟悉程度，以及是否有结构化的排查思路。

**💡 满分回答 (STAR 法则 + 递进排查)：**
1. **确认现象与范围 (Isolate)**：首先看监控大盘（Prometheus/Grafana），确认是单台机器掉线，还是整个 Job 全部卡死。通常 GPU Volatile Uncorr. ECC 错误或单网卡掉线会引发整个 Ring 环的阻塞。
2. **打开 NCCL 调试日志**：我会立即注入环境变量 `NCCL_DEBUG=INFO` 和 `NCCL_DEBUG_SUBSYS=INIT,NET,ENV` 重新拉起或查看留存日志，寻找最后一次成功的通信原语。
3. **网络与物理层排查**：
   - 运行 `ibstat` 和 `ibv_devinfo` 检查 IB 网卡状态，看是否有 `Port Down`。
   - 使用 `nccl-tests` (如 `all_reduce_perf`) 单独在疑似故障的节点间做点对点带压测试，排除硬件物理连线损坏。
4. **软件与逻辑层排查**：
   - 使用 `gdb -p <pid>` 或 `py-spy dump --pid <pid>` 打印当前 Python 进程的调用栈。绝大多数情况会发现卡在 `ncclAllReduce` 或 `torch.distributed.barrier()`。
   - **典型死锁原因**：DDP 模式下，某个 Rank 由于 `if/else` 分支逻辑没有进入 `all_reduce`，导致其他 Rank 都在死等；或者输入 Tensor 的 Shape 不一致导致通信大小不对齐卡死。
5. **恢复机制**：依赖我们自研的 Watchdog 脚本和心跳机制，结合 PyTorch 的 `NCCL_ASYNC_ERROR_HANDLING=1`，一旦检测到 3 分钟超时 (Timeout)，自动 Kill 任务并拉起，从上一个 Checkpoint 继续训练，同时将故障节点隔离（Cordon）。

### ❓ 真题 2：训练中后期 Loss 突然出现 Spike（突刺/飞车），最后变成 NaN，你怎么解决？
**[面试官意图]** 考察对混合精度训练（AMP）、数值稳定性（Numerical Stability）以及算子越界的理解。

**💡 满分回答：**
这通常是由于**数值溢出 (Overflow)** 导致的。
1. **梯度与激活值分析**：首先通过 TensorBoard 或 W&B 观察是在哪一层开始 Spike 的。是 Gradient Norm 爆炸？还是某个特定层的 Activation 异常？
2. **FP16 溢出与 Loss Scaling**：如果使用的是 FP16 混合精度训练，动态 Loss Scaling 可能没有及时下调。FP16 的最大值只有 65504，非常容易在 `LayerNorm` 的方差计算或者 `Softmax` 的指数运算中溢出。
3. **根本解法 (Fixes)**：
   - **算子层面**：在 Softmax 前减去 Max 值 (Safe Softmax)，或者在 RMSNorm 中强制将累加器提升为 FP32。
   - **架构层面**：排查数据中是否存在异常 Token 或空白数据导致分母为 0；若是 BF16 训练，由于其指数位与 FP32 一致（表示范围大），很少出现数值溢出，如果是 BF16 还出现 NaN，通常是学习率（LR）设置过大，或者是数据集存在脏数据（例如无穷大 padding）。
   - **快速恢复**：跳过出现 Spike 的那个 Data Batch，回滚到前 100 步的 Checkpoint，并稍微降低 Learning Rate (LR Decay) 重新跨越这一段数据。

### ❓ 真题 3：线上推理服务 (vLLM) 遇到高并发流量打入，TTFT (首字延迟) 增加到了 5 秒以上，如何优化？
**[面试官意图]** 考察对推理引擎瓶颈 (Prefill vs Decode)、调度策略以及 KV Cache 的深入理解。

**💡 满分回答：**
TTFT 飙升意味着**Prefill (预填充) 阶段被严重阻塞**。
1. **定位瓶颈**：通过 OpenTelemetry 追踪请求，确认是排队在 Gateway 还是阻塞在 vLLM 的 Scheduler 中。如果是 vLLM 内部阻塞，说明 GPU 的 Compute Bound 已达上限。
2. **Chunked Prefill 优化**：传统的 Continuous Batching 中，Prefill 阶段由于需要计算长 Prompt 的完整 Attention，会霸占 GPU 资源，导致其他正在 Decode (生成) 的请求产生卡顿。我会开启 **Chunked Prefill** 机制，将长 Prompt 的 Prefill 强制切分为固定长度（例如 512 tokens）的 Chunk，与 Decode 任务混合调度（Mix Batching），这样虽然增加了少许整体延迟，但能保证极低的 TTFT 和平滑的 TPOT（输出延迟）。
3. **KV Cache 命中率提升**：大量并发意味着大量重复的首图、系统 Prompt。我会引入 **SGLang 的 RadixAttention (前缀树缓存)** 或者在接入层增加 **Semantic Cache (语义缓存)**，复用已计算好的 KV Cache，直接免除重复的 Prefill 计算。
4. **熔断与限流**：如果流量远超集群承载上限，必须在 Gateway 层触发令牌桶限流，丢弃部分请求以保全集群不雪崩，或者降级至更小的模型 (Fallback to 8B model)。
